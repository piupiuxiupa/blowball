## Why

Blowball 当前只能由消息请求或会话队列触发 Agent，无法在用户离线时按约定时间执行日报、巡检等任务。需要增加用户级、持久化的定时任务，并复用既有完整 Turn 执行链路，而不是为定时任务维护第二套 Agent 实现或强制新增服务。

## What Changes

- 提供已鉴权的定时任务管理及运行历史 API，支持创建、查询、修改、暂停、恢复、删除任务；第一版支持单次 `at` 和标准五字段 `cron`，明确保存 IANA 时区。
- 支持每次创建独立会话，以及显式指定用户自己的既有会话；默认独立会话，结果、工具活动、产物和用量沿用现有持久化能力。
- 将任务定义与单次触发记录保存在 MySQL；调度器通过原子领取和稳定执行身份处理多副本、停机恢复及重复扫描，不将未来任务长期放入 Redis Run 或会话队列。
- 从现有消息处理链路提供不依赖 Gin/SSE 的内部 Turn 提交入口，让 HTTP、会话队列接续和定时任务共享完整执行链路。
- 调度模块与 Agent 执行在代码层解耦；启用后只在现有 `agent / all` 进程运行，不增加 `scheduler / worker` 角色、独立服务或消息中间件。
- 明确第一版执行策略：停机后合并补跑一次，同一任务不重叠，既有会话忙时跳过，不自动重跑已经开始或启动结果不确定的 Agent 执行。
- 按任务所有者重新验证账号、会话和执行权限，运行时获取当前 LLM 凭证；不持久化创建任务时的登录 JWT，后台需要的用户 JWT 仅在授权检查后短期签发并保存在内存。
- 增加默认关闭的调度开关、轮询间隔、后台并发上限及运行时限，保持关闭时交互聊天行为不变。

第一版不包含 Agent 自主管理任务的工具、自然语言时间解析、手动立即运行、外部通知渠道、通用工作流编排或工具副作用的自动业务重试。上述范围和执行策略是本 proposal 的建议默认值，不是已经实现的功能。

## Capabilities

### New Capabilities

- `scheduled-agent-tasks`: 用户级任务管理、时间规则、持久化触发与运行历史、后台授权、会话策略、停机恢复、重叠及执行限制。

### Modified Capabilities

- `service-roles`: 明确定时任务管理路由属于 `api / all`，后台调度属于 `agent / all`，保持现有角色及故障隔离边界。
- `turn-run-lifecycle`: 增加无 HTTP/SSE 的内部 Turn 提交要求，复用既有执行、事件、持久化与取消能力，同时保持交互请求的 Run 身份、排队及降级语义。

## Impact

- 应用层：影响消息/Turn handler 中的提交与启动边界、服务层、Run 管理及 `cmd/blowball` 的角色 wiring 和停机顺序；Agent 编排和工具实现不新增第二套代码。
- 持久化：新增任务及触发记录模型、MySQL Store 方法和顺序迁移；运行历史不能依赖 Redis 的短期保留窗口。
- HTTP：新增 `/api/v1/scheduled-tasks`、单任务资源及任务运行历史接口；实施时同步更新 `api/openapi.yaml`。
- 配置与依赖：实施时更新 `config.example.yaml`；增加标准 cron 解析依赖，但不引入内存任务表作为事实源、外部调度平台或新的队列服务。
- 运维：继续使用现有 MySQL、Redis 和工作空间存储；多机执行沿用共享工作空间要求。现有数据库需手动应用迁移，再显式启用调度。
- 验证：新增时间规则、授权、并发领取、故障窗口及无 SSE 执行测试，并保留交互消息、会话队列、Run 生命周期和角色归属回归测试。
