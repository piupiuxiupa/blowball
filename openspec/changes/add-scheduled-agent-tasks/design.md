## Context

Blowball 已有 `all / api / agent` 进程角色。API 角色处理鉴权及 CRUD；Agent 角色持有 Orchestrator、Run registry、流式事件、会话排队及终局持久化。当前 HTTP 直接发起和队列接续已经共用 `MessageStreamHandler.startTurn`，但入口及若干执行类型仍位于 handler 包中。

Redis Run 状态和事件有短期保留窗口，不能承担数天后的调度定义或长期运行历史。MySQL 已保存用户、会话、消息、工具活动、用量及 per-user LLM 凭证；多机执行依赖现有共享工作空间配置。

本设计采用前序讨论确定的部署方向：调度与执行逻辑解耦，第一版仍运行在现有 Agent 进程内。时间策略、会话策略和第一版接口范围是本次 proposal 的建议默认值。

## Goals / Non-Goals

**Goals:**

- 用户离线时仍能执行单次和周期任务，任务与执行历史在重启后保留。
- HTTP、会话队列接续和定时任务共用完整 Turn 执行链路。
- 多副本扫描不重复物化同一个计划槽位，同一任务不并行执行。
- 明确后台身份、停机补跑、启动不确定性、超时及结果读取语义。
- 保持现有 HTTP/SSE、会话队列、用户凭证和工作空间隔离行为。

**Non-Goals:**

- 新增独立 Scheduler/Worker 服务、运行角色、消息中间件或工作流平台。
- Agent 自主管理任务工具、自然语言时间解析、秒级调度、固定间隔 `every` 或手动立即运行。
- 邮件、Webhook、Slack 等外部投递，以及“无变化则静默”的监控产品层。
- 自动重新执行已启动的任务、工具副作用的 exactly-once 保证或跨任务 DAG。
- 第一版 UI、历史自动清理和交互/后台执行的物理资源隔离。

## Decisions

### 1. 调度是现有 Agent 进程中的独立模块

```text
api / all                         agent / all
任务管理 API                       HTTP 消息 / 会话队列接续
      │                                      │
      ▼                                      ▼
MySQL 任务与触发记录 ◀── Scheduler ──▶ 统一 Turn 执行入口
                                            │
                                     Run / Orchestrator
                                            │
                                    消息、产物、用量、状态
```

任务 CRUD 服务只依赖配置校验和 Store，不构造 LLM 客户端、工具注册表或执行沙箱。Scheduler 只决定触发时间、领取记录并提交执行，不直接调用模型。API 角色不可用时，Agent 角色仍能从持久化任务启动执行；Agent 角色不可用时，API 角色仍可管理任务。

不新增跨进程 RPC 或通用 Worker 队列。以后独立部署时可以替换提交适配器，但本次不预先实现远程协议或新的运行角色。

**替代方案：** 独立 Scheduler 服务能独立升级，但第一版增加部署与投递故障窗口，且无法隔离最终执行资源；复制一套“定时 Agent 服务”会重复 Turn 生命周期逻辑。

### 2. 共享完整、无传输依赖的 Turn 执行入口

提供中立的内部 Turn 执行模块，建议位于 `internal/turn`。只迁移共享执行所需的类型和代码，避免 `service -> handler` 依赖或包循环；HTTP 解析、响应头和 SSE 订阅继续属于 handler。

统一入口接收经过鉴权的身份、会话、文本、已解析模型选择和 Run 身份，处理历史恢复、记忆召回、压缩、Run 认领、事件 drainer、Agent 执行、增量及终局持久化、用量、产物和取消。无 SSE 订阅者时仍必须启动事件消费和持久化，不能让 Hub 因无人读取而阻塞。

HTTP 的 `trace_id == run_id`、附件校验、排队顺序和 Redis 故障降级保持原样。定时来源使用预留的稳定 Run ID，并采用明确的后台 admission 策略：忙时跳过，Redis 不可用时不降级为无锁执行。

只增加必要的启动前授权/fence 检查和终局通知边界，使 Scheduler 能持久化任务运行状态；不创建通用可插拔 Hook 框架，不修改 Agent 编排算法。

**替代方案：** 直接调用 `Agent.Run` 会遗漏上下文、费用和持久化；模拟 HTTP/SSE 会耦合登录会话、传输和后台执行。

### 3. MySQL 保存任务及持久化待执行记录

新增两个逻辑数据集合：

| 数据 | 主要内容 |
| --- | --- |
| `scheduled_tasks` | `task_id`、`user_id`、name、prompt、时间规则、时区、会话策略、model/effort、`enabled`、`next_run_at`、revision、创建/更新时间、`deleted_at` |
| `scheduled_task_runs` | occurrence ID、task ID、配置快照与 revision、`scheduled_for`、稳定 Run ID/会话 ID、状态、领取 token/租约、开始/结束时间、错误或跳过原因 |

任务配置不保存登录 JWT、密码或 LLM token。触发记录保存非秘密的执行快照；LLM 凭证在执行时按用户重新解析，不复制到触发记录。

`(task_id, scheduled_for)` 为唯一槽位身份，时间以 UTC 精度保存。任务 due 索引和待执行/租约索引用于有界批次扫描。领取时间和租约比较使用数据库 UTC 时间；纯时间计算与测试支持可注入时钟。

在短事务中锁定任务、插入本次触发记录并推进 `next_run_at`，不存在“先推进时间，后入队失败”的丢失窗口。`pending` 触发记录本身就是持久化待执行表，进程内 channel 只能用于唤醒，不能是事实源。

`at` 在首次物化后将 `next_run_at` 清空，代表该时间规则已经消费，但不撤销已物化触发的执行授权。修改 `run_at` 为新的未来时间可以显式重新安排任务；仅切换 `enabled` 不会重放已消费槽位。

**替代方案：** 内存 cron 注册表重启易丢任务；长期 Redis Run/会话队列条目与 TTL、短期凭证和消息历史时序不匹配。增加独立 outbox 表在当前规模下没有必要。

### 4. 结构化时间规则，而不是模型计时

第一版仅接受：

- `at`：带时区偏移的 RFC3339 `run_at`，创建或修改时间规则时必须在未来。
- `cron`：标准五字段表达式与独立 IANA `timezone`，不接受秒字段、`@every`、宏或表达式内时区前缀。

两个类型都保存明确的时区，响应中的绝对时间使用 UTC。Cron 解析建议复用 `github.com/robfig/cron/v3` 的标准 Parser/Next 能力，不使用其内存 Job 注册作为任务存储。适配层先校验字段数量和结构，再解析。

时区按 IANA 规则计算；夏令时不存在的本地时间跳过，重复本地时间对应的不同 UTC 槽位可以分别触发。测试必须覆盖默认部署时区不同于任务时区的情况，不依赖宿主机本地时区。

停机或轮询落后时采用**合并补跑一次**：物化数据库保存的最早未处理 `next_run_at`，cron 的下一次时间直接计算为严格晚于当前时间的槽位，不逐个重放历史槽位；单次任务只补一次。主动暂停期间不补 cron，恢复时从当前时间计算下一次；未消费的单次任务恢复后仍可补跑。

### 5. 两层互斥，后台不插入聊天 FIFO

锁定任务行时检查该任务的非终态触发。同一任务已有 `pending / preparing / launching / running` 触发时，新到期槽位记录为 `skipped: TASK_OVERLAP`，并推进下一次时间，不累计一串待执行任务。

`session.mode=new` 默认为每次触发建立独立会话，不把前次完整对话附加到下一次；仍按现有规则使用用户 workspace、skills 和跨会话记忆。触发记录预留稳定会话 ID，准备阶段幂等创建，重复准备不创建多个会话。

`session.mode=existing` 必须指定属于当前用户的会话，并在执行时复查。后台 admission 原子检查会话认领和队列：存在运行或待处理聊天消息即 `skipped: SESSION_BUSY`，无论交互消息排队开关如何，都不插队、不抢占或取消聊天。Redis 无法确认互斥时不启动模型。

**替代方案：** 后台默认进入会话 FIFO 会改变聊天顺序与延迟；允许同任务重叠易造成重复副作用。第一版不暴露可配置的多种重叠策略。

### 6. 分阶段恢复，不声称副作用恰好一次

内部状态大致为：

```text
pending -> preparing -> launching -> running -> succeeded / error
   │           │             │          └── cancelled / interrupted
   └── skipped / cancelled   └── 启动结果未知时 interrupted
```

- `pending / preparing` 尚未允许 Agent 执行。准备仅进行可幂等重做的工作，租约失效后可重新领取；领取 token 必须在下一阶段校验，过期领取者不能启动。
- 在进入可能启动执行的窗口前，先持久化 `launching`。统一入口在首个执行写入/模型调用前，原子校验领取 token、任务授权和运行状态，提交启动 fence；与暂停/删除竞争时以该 fence 为先后边界。
- 提交明确返回 `not_started`，且未跨过启动 fence 时，可有界重试或以 busy/validation 结果终止。提交是否成功不明确时，不退回待执行队列盲目重跑。
- `launching / running` 在重启后先检查 Redis Run 状态和存活。仍存活则跟踪；已终局则补记终态；无法确定或运行进程已死则记录 `interrupted`，不重新执行业务。
- 终局状态在共享 Turn 完成终局消息持久化后回写 MySQL，并做有界重试。Redis 元数据过期且没有可靠终态证据时，保守记录中断/结果未知，保留诊断而不是猜测成功。

安全重试的尝试次数和下次重试时间保存在触发记录中，重启不重置上限。稳定 ID、唯一键和启动 fence 防止已知的重复启动，但不能保证外部接口副作用 exactly-once。该设计选择“不自动重跑不确定的业务”而不是在故障窗口中保证每次都最终执行。

### 7. 后台身份是任务授权，不是保存旧登录会话

创建任务必须来自有效 JWT，所有者从鉴权上下文确定，不接受客户端指定他人 `user_id`。任务定义即该用户对保存指令的后台执行授权，不授予超出该用户现有工具和工作空间权限的能力。

准备及启动 fence 前复查任务未删除、未暂停、所有者账号仍为 active，以及目标会话归属。账号不可用或既有目标会话消失时，记录明确跳过原因并暂停任务，避免周期性继续尝试。

LLM 解析沿用 `user-llm-token`：配置了用户 token 则使用当前用户 token；未配置才使用全局 fallback；用户凭证认证失败不回退到全局凭证。

Skill/MCP 市场等需要用户 JWT 的调用，经受信任的授权服务在检查后为同一用户签发短期执行 JWT，时限覆盖单次运行与有界收尾。JWT 仅通过现有内存 context 传递，不保存到任务/触发表、日志、raw capture、工具参数或 bash 环境中；不新增公开的免密码签发端点。外部市场拒绝凭证时遵守现有 fail-closed 行为。

暂停/删除阻止尚未越过启动 fence 的触发；已开始的执行继续走现有 Run 生命周期，用户通过现有取消端点显式取消。任务修改只影响以后物化的快照，不能悄悄改变运行中的指令。

### 8. 管理 API 与站内结果读取

| 方法与资源 | 行为 |
| --- | --- |
| `POST /api/v1/scheduled-tasks` | 创建任务，201 返回任务和 `next_run_at` |
| `GET /api/v1/scheduled-tasks` | 按所有者列出未删除任务 |
| `GET /api/v1/scheduled-tasks/{task_id}` | 读取单任务 |
| `PATCH /api/v1/scheduled-tasks/{task_id}` | 修改配置或 `enabled`；暂停/恢复不另设端点 |
| `DELETE /api/v1/scheduled-tasks/{task_id}` | 软删除任务并阻止未来及尚未启动的触发，204 |
| `GET /api/v1/scheduled-tasks/{task_id}/runs` | 读取该用户该任务的触发和运行历史 |

Task 主要字段为非空 name/prompt、schedule、session、可选 model/reasoning_effort、enabled；enabled 默认 true，省略会话策略时为 new，省略 model/effort 时沿用现有部署默认选择。时间规则、会话策略和模型参数非法返回 400；他人或不存在的任务/会话返回 404；未鉴权返回 401。

列表使用 `limit / offset`，默认 20、上限 100；任务按创建时间倒序，运行按 `scheduled_for` 和 ID 倒序。运行历史包含状态、原因、计划/实际时间、session_id 和稳定 run_id；完整内容沿用会话历史和 Run 事件接口，Redis 保留窗到期后不删除 MySQL 运行历史。用户主动删除会话后，运行历史保留执行事实但不再保证对话内容仍可读取。

新接口及错误、分页、时间和凭证保密规则在实施时写入 `api/openapi.yaml`，本 proposal 不直接修改已发布契约。

### 9. 有界运行与有序停机

配置建议：

| 配置 | 默认值 |
| --- | --- |
| `scheduled_tasks.enabled` | false |
| `scheduled_tasks.poll_interval` | 5s |
| `scheduled_tasks.max_concurrent` | 4，按 Agent 进程 |
| `scheduled_tasks.max_run_duration` | 10m |

非正间隔、并发和时限拒绝加载。开关只控制后台运行，迁移就绪后管理 API 不依赖调度器在线。关闭时不启动调度/恢复循环，不改变聊天 admission、事件或凭证行为。

准备领取采用短租约和 token 比较；安全的未启动失败最多重试三次并退避，终局回写沿用有界重试思路。这些第一版内部上限不增加用户可配置重试策略。

运行时限从跨过启动 fence 开始计时，超时通过现有取消机制中止，保留部分输出，运行历史记录 `cancelled: TASK_TIMEOUT`。后台并发上限不声称隔离聊天 CPU、内存或网关配额。

优雅关闭先停止新物化和新投递、撤销未开始的领取，再配合现有队列停机 gate 和 Run registry 取消/等待已开始执行，等待有界终局持久化后退出；不能出现关闭 gate 后新增 Turn。

## Risks / Trade-offs

- [与聊天共用执行资源] → 有界后台并发和时限；需要硬隔离时另提后台 Worker 部署，不复制执行代码。
- [SQL 与 Redis 之间启动结果不确定] → 分阶段记录、启动 fence、稳定 ID 及保守中断；接受极端窗口中“未执行但被记为中断”，不盲目重做副作用。
- [终态回写失败或 Redis 过期] → 有界重试和周期恢复，缺乏证据时显式记录未知/中断。
- [动态修改、暂停、删除与领取竞争] → 配置快照、事务检查和启动 fence 定义先后关系。
- [短期后台 JWT 与外部市场兼容性] → 使用现有签发格式和用户身份，集成测试覆盖过期及拒绝；不增加通用特权凭证 fallback。
- [时间规则与夏令时差异] → 标准五字段解析、结构化 IANA 时区、UTC 槽位及边界测试。
- [运行历史及独立会话持续增长] → 分页查询、适当索引和容量观测；本次不自动删除用户数据。

## Migration Plan

1. 先用特征测试固定现有 HTTP、排队、SSE、取消和持久化行为，再提取共享 Turn 入口。
2. 实施时增加下一条顺序 SQL 迁移，创建任务及触发记录表、唯一键和扫描索引；不修改已有用户数据。
3. 更新 OpenAPI、配置示例和部署说明。默认关闭发布，现有数据库先手动迁移。
4. 在测试环境启用，验证同进程及 `api / agent` 分拆部署、重启、多副本和后台授权，再启用生产调度。
5. 回退时关闭调度开关并有序重启 Agent 进程，保留任务及运行历史；不删除表、不重放已消费槽位，正常聊天继续工作。移除新增表不是自动回滚步骤。

## Open Questions

- 用户是否希望第一版即提供 Agent 管理任务工具或 UI？当前默认 REST 管理，后续可单独提案。
- 日报/巡检是否需要每个任务固定会话？当前默认每次独立，既有会话需显式指定。
- 是否有需要“错过即放弃”的业务？当前统一合并补跑一次，不提供多种 misfire 策略。
- 生产后台并发及运行时限需要结合实际负载调整；是否需要物理隔离另行评估。

这些问题是产品确认点，不阻止按本设计明确的默认行为实施；变更默认值时必须同步 proposal、specs 和 tasks。
