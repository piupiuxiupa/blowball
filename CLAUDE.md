# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

Blowball is a Go backend for a multi-agent chat workspace. It exposes a JWT-secured HTTP API (Gin), persists sessions/messages through a Redis-first write-behind path (Redis ingest queue + read cache, background flusher into MySQL), and orchestrates OpenAI-backed agents. (The React frontend lives in the separate `blowball-frontend` repo.)

## Common commands

All backend commands run from the repository root.

### Backend

The server and the seed CLI are a single cobra binary `bin/blowball` with `serve` and `seed` subcommands sharing persistent `-f`/`--config` (config path, default `config.yaml`) and `-d`/`--data-dir` (runtime root, default `.`) flags. The runtime root holds `data/`, `logs/`, and `skills/`; with the default `-d .` these resolve to `./data`, `./logs`, `./skills`.

```bash
# Build the unified blowball binary (serve + seed subcommands)
make build

# Run the server (builds first): ./bin/blowball serve
make run

# Run the server under a dedicated runtime root (-d) and config (-f)
./bin/blowball serve -d /var/lib/blowball -f /etc/blowball/config.yaml

# Select a process role (default --role all == the pre-split monolith on server.port).
# Run the two split roles against the SAME -d root so they share the data plane:
./bin/blowball serve --role api   -d /var/lib/blowball -f /etc/blowball/config.yaml   # CRUD on server.port (8080)
./bin/blowball serve --role agent -d /var/lib/blowball -f /etc/blowball/config.yaml   # streaming + /mcp/tools on server.agent_port (8081)
# Rollback: stop both role processes and run plain `serve` (== --role all) on server.port.

# Create a user (password is prompted securely)
./bin/blowball seed --username alice
./bin/blowball seed --username alice --password 's3cret' --dry-run   # preview hash only

# Run all Go tests with race detection
make test

# Run a single package's tests
go test ./internal/agent/...

# Run a single test
go test ./internal/agent/ -run TestConfuciusDispatchesSubAgent

# Run integration tests (uses fakes for MySQL/LLM, real orchestrator + handlers)
go test ./test/integration/...

# Static analysis
make lint

# Clean build artifacts
make clean
```

### Executor tools (Linux only)

The `bash` tool requires [bubblewrap](https://github.com/containers/bubblewrap) (`bwrap`) and an environment that allows unprivileged user namespaces. It is automatically skipped on macOS and Windows. (The dedicated `python`/`pip_install` executors were removed; run Python code and pip installs through `bash`.) To enable `bash` on Linux:

```bash
# Install bubblewrap (Debian/Ubuntu example)
sudo apt install bubblewrap

# Enable in config.yaml
# tools:
#   executor:
#     bash:
#       enabled: true
#       # network defaults to true so pip-via-bash (python3 -m pip install) can
#       # reach PyPI out of the box; set to false to tighten.
```

Run Python code via `bash` (`python3 ...`) and install packages via `python3 -m pip install --target /workspace/.pip <pkg>` inside the sandbox. `/workspace/.pip` is on `PYTHONPATH` in every `bash` sandbox, so packages installed by the agent are immediately importable by later `python3` invocations without manipulating `sys.path`. If `bash` is enabled but `bwrap` is missing, the server exits with a fatal error. Keep `enabled: false` (the default) to run without bubblewrap.

The runtime root (`-d`) holds a fourth subdir `{data-dir}/tools`, created at startup alongside `data`/`logs`/`skills`. Operators drop CLI binaries (e.g. `node`, custom CLIs) here to expose them inside the `bash` sandbox: the directory is mounted read-only at the in-sandbox `$HOME/.local/bin` (`/home/blowball/.local/bin`), and `$HOME/.local/bin` is prepended to `PATH`. The directory is optional content-wise (an empty dir binds harmlessly), and there is no API to manage it — operators place files directly on disk. See the `internal/tool/executor/` note below for the full sandbox `$HOME`/`PATH` behavior.

Operator environment literals (`tools.executor.bash.env`): a `KEY: value` map injected into every `bash` sandbox, building the environment in three precedence tiers (low → high): (1) the **host allowlist** — host-process vars whose names match `allowed_env_patterns` (glob); (2) **operator literals** from `env`, overriding same-named host-allowlist vars; (3) **forced invariants** — always applied last and always winning: `HOME` forced to the synthetic sandbox home (`/home/blowball`), `$HOME/.local/bin` prepended to `PATH`, `/workspace/.pip` prepended to `PYTHONPATH`. Prefer `env` (not host-export + `allowed_env_patterns`) for shared operator-owned config — pip/npm mirrors, corporate proxies, feature flags — so `config.yaml` is the single source of truth:

```yaml
# tools:
#   executor:
#     bash:
#       env:
#         PIP_INDEX_URL: "https://pypi.mirrors.example.com/simple"
#         HTTPS_PROXY: "${CORP_PROXY}"   # value expands ${VAR} from the host
#         NODE_USE_ENV_PROXY: "1"
```

Values expand `${VAR}` / `${VAR:default}` from the host like every config string, so reference secrets via `${SECRET}` (e.g. `OPENAI_API_KEY: "${OPENAI_API_KEY}"`) instead of hard-coding them — `env` shares the same trust boundary as `openai.api_key`/`jwt.secret`, and the `.blowball` namespace is already blocked from agent file tools. `HOME` is a reserved key (config load fails fast if set); other key names must match `^[A-Za-z_][A-Za-z0-9_]*$`. An omitted/empty `env` is zero behavior change.

## High-level architecture

### Backend request flow

The unified binary lives in `cmd/blowball/`: `main.go` wires the cobra root (`serve`/`seed` subcommands + persistent `-f`/`-d` flags), `serve.go` holds the server bootstrap (`serveRun`), and `seed.go` holds the user-creation subcommand.

The `serve` subcommand bootstraps the application in a strict sequence: resolve `--role`/`-f`/`-d` → shared setup (`setupRuntime`: load config (`-f`, with `${VAR}` env expansion) → derive `dataDir`/`logDir`/`skillsDir`/`toolsDir` from `-d` → `MkdirAll({d}/logs)` → initialize the zap logger with a role-scoped filename (tee console + file under `{d}/logs/blowball[-api|-agent].log`, rotated by lumberjack) → enforce the role-aware `openai.api_key` requirement → connect MySQL/Redis → create the filesystem store under `{d}/data` → `MkdirAll({d}/skills)` → `MkdirAll({d}/tools)` → apply Landlock sandboxing (read-write for `data`/`logs`/`skills`, read-only for `tools`; Linux-only)) → build the shared `SessionService` → register routes by role via `wireAPI`/`wireAgent` → start a gracefully-shutdown HTTP listener. The log directory is created and the log file opened before the logger emits its first line, and before Landlock is applied, so lumberjack's post-rotation reopen stays inside the sandbox.

### Deployment roles (`--role`)

`serve` selects a process role via `--role all|api|agent` (default `all`). The role decides which route partition the process registers, which listener it opens, and which log file it writes. This lets agent execution run as an independent process so a surge or crash in the agent path cannot take the CRUD API down, while the data plane stays shared and unchanged (Phase 1: same-machine, shared local filesystem; cross-host scaling and object storage are out of scope).

| Role | Routes registered | Listener | Log file | Wires |
|------|-------------------|----------|----------|-------|
| `all` (default) | full set (API ∪ agent) on one engine | `server.port` (default 8080) | `blowball.log` | everything — identical to the pre-split monolith (dev, tests, rollback) |
| `api` | CRUD only: auth, session CRUD, message-history read, title update, workspace file CRUD, skills list, model catalog list (`GET /api/v1/models`) | `server.port` | `blowball-api.log` | `wireAPI` — CRUD services/handlers only; **no** orchestrator, OpenAI client, tool registry, or MCP manager. A missing `openai.api_key` is a warning, not fatal (the api role never calls the LLM). |
| `agent` | streaming message endpoint (`POST /sessions/:id/messages`), turn lifecycle (`POST /sessions/:id/turns/:run_id/cancel`, `GET .../turns/:run_id/events`) + `GET /api/v1/mcp/tools` (all JWT-authed) | `server.agent_port` (default 8081) | `blowball-agent.log` | `wireAgent` — tool registry, MCP manager, OpenAI client, orchestrator, `TitleService`, the streaming handler, the turn-run registry (`internal/run`), and the turn-lifecycle handlers; owns the full streaming-turn pipeline (lookup → recover → claim → orchestrate → SSE → persist → title → run finalize). |

Route registration is partitioned in `internal/handler/router.go`: `RegisterAPIRoutes` / `RegisterAgentRoutes` each mount their own subset behind `AuthMiddleware` (middleware order is Recovery → Trace → CORS → Auth on every engine); `RegisterRoutes` is the union used by the `all` role and the integration test harness. The streaming handler (`MessageStreamHandler`, `internal/handler/message_stream.go`) is wired only by the agent role; the api role's `SessionHandler` is CRUD-only and takes no orchestrator, so the api process has a compile-time-honest boundary against the agent layer.

**Shared data plane:** both roles derive `data`/`logs`/`skills`/`tools` from the same `-d` root and connect the same MySQL/Redis/local FS — the Redis-first write-behind persistence, `xizhi` workspace tools, executor sandbox, and Landlock policy behave exactly as in the monolith. A turn persisted by the agent role is readable by the api role through the shared store (both roles share the `msgs:buffer` queue and the synchronous drain; only the agent/all roles run the flusher goroutine). When `storage.workspace.backend: shared` (see `workspace-shared-storage`), the `data` subtree is a shared POSIX filesystem (operator-mounted, MinIO-backed JuiceFS), so the data plane is shared **across machines** too — api/agent instances on different hosts read/write one per-user data tree over the network FS, with all POSIX file operations transparent and unchanged.

**External request routing is out of scope.** How traffic reaches each role's port (reverse proxy, gateway, ingress) is operator-managed; blowball only listens on the role's port and logs `role`, `port`, and the registered route groups at startup. Pointing the streaming route at the api port (or running two `api` roles) surfaces as 404s at the routing layer — by design.

HTTP routes live in `internal/handler/router.go`. Protected routes use `middleware.AuthMiddleware` (JWT Bearer validation) after `TraceMiddleware` and CORS. Key endpoints:

A chat request flows: `MessageStreamHandler.SendMessage` (agent role) → session ownership check → `MessageService.RecoverMessages` (load history) → Redis `SET NX` session-run claim (409 `SESSION_BUSY` with the active `run_id` on a running turn; a claim transport failure degrades to unguarded execution, matching the persistence fallback convention) → `OrchestratorRunner.Handle` on a **turn-scoped context held by the run registry** (`internal/run`) → the adapter's event-collection goroutine mirrors events into a hub whose single consumer (the `run.StartDrainer` pump) appends every event (done included) to the Redis Stream `run:{rid}:events` (`rid` = the request's trace id, delivered via the `X-Run-Id` response header and `meta.run_id` on every event) → both the originating SSE response and the resume endpoint are the SAME subscription loop (`writeRunEventStream`) reading the stream (XRANGE replay + XREAD BLOCK tail; SSE `id:` line = stream entry id, so `Last-Event-ID` resume is exact). **Client disconnect does not cancel the turn** (turn-detach-resume): the turn goroutine finalizes the run on completion (terminal status → session-claim release → 60s retain-window expiry; 30min TTL backstops crashes), then the handler persists via `SaveMessagesBatch` on a detached context. Title generation runs asynchronously after the first assistant response. A status-running run whose heartbeat (`run:{rid}:alive`, 5s beat / 15s TTL) expired is dead: cancel force-clears it to `interrupted`, and an attach synthesizes a terminal `done` with `usage.error="interrupted..."`. Graceful shutdown cancels all registry runs (bounded by `ShutdownTimeout`) before the write-behind flushers drain.

### Workspace file routing

Because gin does not allow a static `/download` segment alongside a `/*path` wildcard at the same tree node, workspace file GET routes share a single catch-all at `/api/v1/workspace/files/*path`. The handler dispatches internally:

- `.../files/download/*path` → `WorkspaceHandler.TokenDownload` (query-token auth via `QueryTokenAuthMW`).
- `.../files/*path/content` → `WorkspaceHandler.Content` (text content; rejects binary files).
- `.../files/*path/onlyoffice-config` → `WorkspaceHandler.OnlyOfficeConfig` (signs a DocEditor config; header auth).
- `.../files/*path/onlyoffice-version-config?versionId=` → `WorkspaceHandler.OnlyOfficeVersionConfig` (view-only config for a historical office-vers version; header auth).
- `.../files/*path` → `WorkspaceHandler.Download` (header auth).

DELETE uses the same wildcard pattern under a different method. The token-download endpoint exists so browser-native elements (`<a download>`, `<img>`, PDF.js) can access workspace files without custom `Authorization` headers.

OnlyOffice integration: the two `onlyoffice-config` GETs are dispatched by the same GET catch-all (trailing-suffix, like `/content`); the save callback is a standalone `POST /workspace/onlyoffice-callback` registered outside the catch-all so it can carry `QueryTokenAuthMW`. Config is the top-level `onlyoffice` block (`OnlyOfficeConfig` in `internal/config/config.go`): `secret` (HS256, must match the DocumentServer `local.json` secret — when empty the editor-config endpoints return 404), `server_url` (the backing server URL the DocumentServer container uses to reach blowball for `document.url`/`callbackUrl`; defaults to `http://localhost`), plus `version_service_url`/`fileserver` for historical-version rendering. All fields `${VAR}`-expand. Editor configs are HS256-signed server-side so the secret never reaches the browser.

PUT shares the same catch-all and dispatches by suffix via `dispatchWorkspacePut` (mirroring the GET dispatcher): `.../files/*path/content` → `WorkspaceHandler.WriteContent` (atomic text-content write); bare `.../files/*path` → `WorkspaceHandler.Rename` (rename/move, with move-into-folder and optional `overwrite`).

POST shares the same catch-all but registers directly (`authed.POST("/workspace/files/*path", deps.WorkspaceCreate)`) with no suffix dispatcher — there is no `/content` split on POST. `WorkspaceHandler.Create` does a strict create of an empty file or directory selected by the body `{"type": ...}` (409 `ALREADY_EXISTS` on an existing leaf). It does not collide with the static `POST /workspace/upload` route, which diverges at the `/workspace/{upload,files}` node.

### Agent orchestration

The agent layer is in `internal/agent/`.

- `Agent` interface: `Run(ctx, messages, hub)` returns content, usage, and a per-agent `*TurnBreakdown` (Confucius only; leaf agents return nil and the parent aggregates). The breakdown carries `by_agent` (per-agent usage keyed by display name, always including "Confucius") plus turn meta (`parallel` — whether any assistant round dispatched ≥2 tool_calls; `sub_agent_invocations` — ordered invoke_* names; `round_capped` — whether any agent hit its `max_rounds` cap, omitted when false).
- `LLMClient` interface: `StreamChat(ctx, req, onToken)`.
- **Stream idle watchdog** (llm-stream-watchdog capability): when `openai.stream_idle_timeout` is configured (opt-in like `tools.timeouts`; recommended `2m`, zero/unset = disabled, negative rejected at load), every `StreamChat` call through the shared `OpenAIClient` — agent loops, wrap-up rounds, title, compaction summaries — is bounded by the max gap between consecutive SSE frames, with the first gap starting at call issuance (time-to-first-frame covered); total duration is never bounded. A stall aborts with the typed `ErrStreamIdleTimeout` (message carries "timeout" so `isTransientError` routes it into the existing sub-agent retry pipeline unchanged), logs one WARN, and raw-captures as a `kind=error` row (`http_status=0`); caller cancellation still wins any race and keeps its partial `kind=response` row.
- **`finish_reason=length` continuation** (llm-length-continuation capability): when `openai.length_continue` is configured (opt-in; zero/unset block = disabled = a length round still terminates the turn silently as before, any non-zero field enables it with missing siblings defaulted — `expand_step` 8192, `max_retries` 3, negatives fail config load), a round whose LLM response is cut by the output token limit is **continued, not regenerated**: the partial output is kept and the round is re-requested with `MaxTokens = agents.<name>.max_tokens + N × expand_step` (attempt N), up to `max_retries` continuations (attempts do NOT consume `max_rounds`). Content-only truncation appends `assistant(partial)` + a user continuation instruction to the round; a truncated `tool_call` (arguments cut mid-JSON) is kept in the assistant message (B-call-1) but never executed — it gets a synthetic not-executed tool result telling the model to re-issue in smaller chunks, emitted as a `tool_call` (args sanitized to `{}`) + `tool_result` SSE pair, while calls whose arguments parse as JSON dispatch normally before the continuation request (the wire protocol requires every tool_call to be answered). All attempts' token runs are seamless — no event between them, so `MergeEvents` persists the round as one message row; the scaffolding (instruction, synthetic results) is round-local and never event-persisted. All attempts fold into `total`/`by_agent` (real spend; each attempt is its own `llm_raw_log` call with the expanded request visible), but `context_tokens` records only the final attempt's usage. Exhaustion (every attempt length) emits `agent_error` (`length_exhausted`) + `agent_end` and fails the turn with `done.error`, keeping the accumulated content as `finalContent`; the error text deliberately avoids transient-error substrings so sub-agent dispatch never retries it. Covered via the shared `runLLMRound` helper (`internal/agent/lengthcontinue.go`) at the three agent loops and `runWrapUpRound`; title generation and compaction summaries are NOT covered. The prevention side pairs with it: `xizhi_write_file`/`xizhi_modify_file` descriptions get a per-agent write-budget sentence (`floor(max_tokens × 0.7)` tokens per single write, chunk larger content) injected at tools[] render time (`internal/agent/tools.go` — the registry is process-wide while `max_tokens` is per-agent), and `xizhi_write_file` gained `mode: "write"|"append"` making chunked multi-write literally executable.
- `OpenAIClient` (`openai_client.go`) implements `LLMClient` with `openai-go/v3`, structured debug logging, and a `toolCallStitcher` that reassembles fragmented tool-call deltas. It also carries an optional `RawCaptureSink` (`rawcapture.go`, llm-raw-capture capability): every `StreamChat` call mints a `call_id`+`seq` pair and emits a `kind=request` record (the exact as-sent params JSON, captured before the stream starts so a mid-stream crash still leaves the request side), **one `kind=chunk` row per SSE frame** (raw = the frame's wire bytes verbatim via `ChatCompletionChunk.RawJSON()` — the fragmented form, not the concatenation; per-call capture is capped at 8MB cumulative with an explicit `{"_truncated":true,...}` marker row, the response row unaffected), and a `kind=response` record (the stitched non-streaming-equivalent `chat.completion` JSON) or `kind=error` record (gateway HTTP status + raw error body; local ctx cancellation is a partial-`response` row, not an error row). Rows of a call order by `frame_index` (request=0, chunks 1..N, response/error last); replay a turn with `ORDER BY seq, frame_index`. Attribution columns (`session_id` via `agent.WithSessionID`, agent name via `agent.WithAgentName` injected at each agent's `Run` entry so round-cap wrap-up rounds inherit it, `trace_id`/`user_id` already in ctx) ride context — the sink never blocks a turn. The production sink (`internal/llmraw`) stages records on the Redis LIST `llm_raw:buffer` (RPUSH per record, best-effort) and a background flusher batch-inserts them into MySQL via atomic `LPOP key count` pops (multi-consumer safe; at-most-once on crash), paced by a 5s ticker with an early flush once the queue crosses 50 records and a final bounded drain on graceful shutdown. Zero-config, always on for agent/all roles; the api role never constructs it.
- `Orchestrator` (`orchestrator.go`) is the per-request entry point. It builds a fresh agent graph via `AgentFactory.Build`, runs `Confucius`, and emits the final `done` event with the authoritative per-agent usage object.

Three agents are configured in `config.yaml`:

- `Confucius` — central orchestrator. Runs a tool-calling loop and can dispatch `invoke_chongzhi` / `invoke_liang` sub-agent calls.
- `Chongzhi` — coding agent with workspace file tools (`xizhi_*`).
- `Liang` — analysis agent without file tools.

### Per-request model selection (per-request-model-selection / model-effort-v2 capability)

The **mandatory** `openai.models` catalog is the single source of per-turn models; agents carry NO model/thinking fields (the old `agents.<name>.model|thinking|reasoning_effort` keys are rejected at load with a migration-pointing error, as are the removed `openai.model` → renamed `openai.title_model`, and the top-level `openai.max_context_tokens` → moved into each catalog entry). Each entry carries `name` (unique), `max_context_tokens` (**positive integer required**), and `thinking` (a capability marker deciding the entry's wire family and gating request effort values); `openai.default_model` picks the default entry (unset → first entry); `openai.default_reasoning_effort` (`none|low|medium|high|xhigh|max`, unset → `none`) is the deployment-level effort default; `openai.title_model` (unset → default entry, need not be in the catalog) drives only the async title generation. All entries share the single gateway (`openai.base_url`/`api_key`).

- **Dual-axis resolution** (`internal/handler/model_selection.go`): every request resolves BOTH axes — `model = request.model ‖ default entry`, `effort = request.reasoning_effort ‖ default_reasoning_effort`; there is no "parameters absent" zero state. Unknown model → 400 `INVALID_MODEL`; invalid effort, or non-`none` effort EXPLICITLY requested on a `thinking: false` entry → 400 `INVALID_EFFORT`; a non-`none` deployment default landing on a `thinking: false` entry is clamped to `none` + WARN (not 400 — the mismatch can't be caught at load since the default entry may think while others don't). If any agent configures `output_schema` and the resolved effort ≠ none → 400 (the runtime twin of the config-level load check: any `output_schema` agent + `default_reasoning_effort ≠ none` fails config load).
- **B2 wire family** (`openai_client.go`): the wire shape follows the resolved entry's `thinking` capability. `thinking: true` → EVERY call sends `reasoning_effort` (the literal `"none"` included — compatible gateways then actually disable thinking; glm keeps thinking on unless `none` is explicit) and maps `max_tokens` → `max_completion_tokens`; `thinking: false` → no `reasoning_effort`, plain `max_tokens`. Sampling parameters (the former always-0 `temperature`) are sent on neither family.
- **Turn config injection**: the handler resolves the request into an `agent.ModelOverride{Model, Thinking (wire-family marker = entry copy), ReasoningEffort}` — always non-zero — passed through `OrchestratorRunner.Handle` → `AgentFactory.Build`, which injects the same value into every agent constructor (Confucius and both per-invocation sub-agent factories): one turn, one model, one effort across Confucius/Chongzhi/Liang, including wrap-up rounds. `max_tokens`, tools, and prompts stay per-agent config.
- **Turn-level records**: the resolved model name rides the run meta (`run:{rid}:meta` `model` field) and `turn_usage.model`; the context-compaction threshold for the turn is `0.8 × the resolved entry's max_context_tokens`.
- `GET /api/v1/models` (api partition) lists the catalog + `default` + `default_reasoning_effort` (the frontend's effort-picker preselection).
- `GET /api/v1/models` (api partition) lists the catalog + default; the implicit catalog returns the synthesized entry so the response shape never forks.

### Context compaction (context-compaction capability)

Long sessions condense their middle history into a structured checkpoint summary when context pressure reaches a fixed **80% of the effective max context** — the request-resolved catalog entry's `max_context_tokens` that turn (per-request-model-selection / model-effort-v2; the catalog is mandatory and every entry's window is a validated positive integer, so every turn has a threshold) — so the model context never grows unbounded into the provider's hard window limit. A configured window must be a positive integer (a negative or fractional value fails config load — yaml.v3 silently truncates fractions, so the loader shadow-checks the raw value).

- **Measurement is authoritative usage, never estimation**: mid-turn checks use the just-finished round's `resp.Usage.PromptTokens+CompletionTokens` (the true size of the next request); turn-start preventive checks use the latest `turn_usage.context_tokens` (the previous turn's *last-round* size, emitted as `usage.meta.context_tokens` on the done event — never the cumulative `total_tokens`) compared against the CURRENT request's selected-model threshold, so switching models re-evaluates old turns against the new window.
- **Two trigger points**, both calling `CompactionService.Compact` (`internal/service/compaction.go`): (1) **mid-turn** — `Confucius.Run` invokes an injected `RoundHook` (`internal/agent/roundhook.go`) after each round's tool results are appended; (2) **turn-start** — `SendMessage` compacts before the first LLM call when the previous turn ended over threshold. Triggers additionally require a non-empty middle (everything between the preserved first message and the retained tail).
- **Mid-turn flow is flush-first** (`TurnEventTap` + `newRoundHook` in `internal/handler/`): the hook takes a *synchronized* snapshot of the turn's collected events (the adapter's event goroutine drains the hub channel before replying, so a flush can never persist a partially-merged token run under a deterministic id), persists them through the ordinary `SaveMessagesBatch` path, then recovers the **durable** history (`CompactionService.RecoverDurable`: bounded write-behind drain + direct MySQL read — the Redis read cache serves unflushed rows with `id=0`, which would make the boundary cursor non-durable), compacts, and rewrites the in-memory `round` to the stitched shape so the loop continues on it.
- **Range selection** happens on the reconstructed agent-message sequence (`MessagesToAgentMessagesIndexed` returns per-message row attribution): the first user message is never shadowed, the last 5 agent messages are retained verbatim, and the cut retreats across tool call/result pairs so they never split. The boundary persists as the composite cursor `(msg_time, msg_index, id)` of the last shadowed row. Re-compaction merges the prior checkpoint with the newly shadowed span into one summary (checkpoint-merge, no stacking).
- **Summary generation** runs on the TURN's selected model through the shared `OpenAIClient` (so the call lands in `llm_raw_log`, attributed to agent `compaction`; `CompactionInput.SummaryModel` defaults to the Confucius model when the caller passes none), with an 8-section structured checkpoint template; only returned text is kept (reasoning/tool_calls discarded). Its cost is recorded on the compaction row, not in `turn_usage`.
- **Storage** (migration `013_context_compaction.sql`): append-only `context_compactions` (latest `(session_id, id)` row wins for stitching; FK cascade with session deletion; no deletion-archive mirror), `sessions.context_compacted` (stitching gate; set LAST in the write order record → Redis cache `compaction:{sid}` → flag, never reset), `turn_usage.context_tokens`, and `messages.client_msg_id` widened to `CHAR(64)` for deterministic ids. Redis `compaction:{session_id}` caches the latest record with the `msgs:` TTL family, miss-backfilled from MySQL; `DelSessionCache` clears it.
- **Idempotent mid-turn persistence**: flushed rows carry deterministic `client_msg_id = {trace_id}:{msg_index}` (user row = `:0`, merged events `:1..N`), so the turn-end save — which pushes only the post-flush suffix to keep the Redis `msgs:` list duplicate-free — collapses any overlap in MySQL via the existing UNIQUE index.
- **Stitched context** (compacted sessions): `[first user message] + [framed summary as one user-role message (<compacted-summary> wrap)] + [everything after the boundary] + [the new user message]`. Missing record/boundary degrades to full history; **the display path (`GET /messages`, the `messages` table, the `msgs:` cache) never sees compaction** — no summary rows, no gaps. Compaction is silent (no SSE events) and never blocks a turn: every failure is a WARN plus fallback.

`Confucius` dispatches tool calls in parallel. Sub-agents receive only the `task` and `context` passed by `Confucius`, stream through the same `stream.Hub`, and cannot recursively invoke other agents. **Per-invocation sub-agent instances + run identity** (subagent-run-identity capability): Confucius holds `SubAgentFactory` values (not instances) for `invoke_chongzhi`/`invoke_liang`; every dispatch builds a fresh Chongzhi/Liang and discards it after the call, so the mutable per-run flags (`ToolCallTracker`'s side-effect flag, `RoundCapTracker`'s cap flag) are isolated per invocation — concurrent same-name invocations can neither suppress each other's retries nor pollute each other's `round_capped` propagation. Retries reuse the SAME instance (one logical call). Read-only construction inputs (config, LLM client, the per-turn MCP manager, `TurnCloser`) stay turn-shared via factory capture. Every event a sub-agent Run emits is stamped by the dispatch layer with `Meta.parent_tool_call_id` = the invoking tool_call id (`stream.TaggedWithRunID` wraps the hub handed to `Run`; agents are unaware — `Agent.Run` takes the `stream.EventHub` producer interface so `*Hub` and tagging views are interchangeable). Confucius's own events and user rows never carry the key. Each agent's tool-calling loop is bounded by a per-agent round cap configurable via `agents.<name>.max_rounds` (default `100`; `0`/unset → default, negative rejected at load). On a cap hit the loop emits a structured `WARN` log and sets `usage.meta.round_capped`, then runs one **tool-disabled wrap-up round** — appending a steering message telling the model the round limit is reached and it must answer from what it has — so the model synthesizes instead of continuing tool-use. The wrap-up's content becomes the final answer; if the wrap-up instead returns `tool_calls` (which cannot be honored — some OpenAI-compatible gateways emit them even with an empty `tools[]`), no content, or errors, the loop emits `agent_error` (code `round_cap_exhausted`) + `done.error` (the previously-silent empty-end case) and never silently returns a tool-call preamble as the answer. A sub-agent hitting its cap propagates `round_capped` to the turn-level `done` event via the `RoundCapTracker` capability.

### Tools, MCP, and skills

Tools are registered in a process-wide `tool.Registry` (`internal/tool/registry.go`). The registry resolves configured tool names to `*ToolSpec` values and renders the OpenAI `tools[]` shape.

Built-in tool families:

Every registry-tool result is rendered into a uniform status envelope before being fed back to the model as the `role="tool"` message body: `{"status":0,"result":<JSON-encoded tool return value>}` on success and `{"status":1,"error":"<message>"}` on failure. The envelope is produced by one shared renderer (`renderToolResult` in `internal/agent/confucius.go`) invoked from all three agents' registry-tool dispatch sites (Confucius/Chongzhi/Liang); `[]byte` and `string` returns are normalized to text before encoding (not base64), and `nil` renders as `result:null`. It is a model-facing signal — and for tool failures it is now the **sole** channel: no `agent_error` SSE event is emitted for a registry-tool failure (the frontend renders tool errors from the `status` field). Other `agent_error` codes (`llm_error`, `unknown_tool`, `bad_args`, `retry`, `round_cap_exhausted`) are unaffected and still fire for genuine agent-level failures. Sub-agent (`invoke_*`) results bypass the envelope: their content is the sub-agent's output/error text verbatim.

- `internal/tool/xizhi/` — workspace file tools (`xizhi_read_file`, `xizhi_write_file`, `xizhi_modify_file`, `xizhi_list_files`, `xizhi_tree`, `xizhi_glob_files`, `xizhi_grep`). Each closure is scoped to the requesting user's workspace root (`data/{userID}/workspace`). `validatePath` rejects absolute paths, `..`, and symlink escapes. `modify_file` requires a unique old-content match. `xizhi_write_file` takes an optional `mode` ("write" default = create-or-overwrite, unchanged; "append" = create-if-missing / append-to-end, returning `{path, size, absolute, appended}`) — the executable form of the chunked-multi-write steering (llm-length-continuation prevention side; the write-budget number `floor(max_tokens×0.7)` is injected into the write/modify descriptions per agent at tools[] render time). `xizhi_read_file` returns cat -n line-numbered content (`<lineNo>\t<line>`, one row per line) plus `start_line`/`total_lines`/`size`/`truncated`, paginated via `offset`/`limit` (default 2000 lines; `truncated` is set when more lines remain), and rejects binary files (NUL-byte sniff) with an error. `xizhi_grep` searches file contents by RE2 regex with an `output_mode` (`content`/`files_with_matches`/`count`; default `content`), optional file-name glob filter, line numbers, context lines (content mode only), and a case-insensitive switch, paginated via `head_limit`/`offset` (default 200 / 0) and reporting `mode`/`applied_limit`/`applied_offset`/`total_files`/`truncated` (request the next page with `offset = offset + head_limit`); it **shells out to system `rg`** (ripgrep) when present on `PATH` (`rg --json`, parsed) and otherwise falls back to a pure-Go RE2 `filepath.WalkDir` engine — both produce identical results (skips binary files, does not follow symlinks, `--no-ignore`). Its `path` argument is **required** (an empty/blank path errors with `xizhi_grep: path is required` rather than falling back to the workspace root) — `"."` explicitly means the root. `list_files`/`tree`/`glob_files` still default an empty path to the root (unchanged). Landlock provides defense-in-depth on Linux.
- `internal/tool/webfetch/` — `webfetch` HTTP fetch tool.
- `internal/tool/executor/` — sandboxed command execution (`bash` only; the dedicated `python`/`pip_install` executors were removed — run Python and pip via `bash`). Only available on Linux when `bwrap` (bubblewrap) is installed. Each invocation runs in a fresh user/mount/pid namespace, binds `data/{userID}/workspace` to `/workspace`, clears the environment and rebuilds it in three precedence tiers (host allowlist via `allowed_env_patterns` < operator literals via `bash.env` < forced invariants: `HOME`, `PATH` prepend, `PYTHONPATH` prepend), and subjects commands to a configured timeout and `max_output_bytes` cap. Network access is enabled by default for `bash` (so `python3 -m pip install` via bash reaches PyPI); operators may set `bash.network: false` to tighten. Installed packages are written to `/workspace/.pip` (via `python3 -m pip install --target /workspace/.pip`) and exposed to later `python3` invocations within `bash` through the injected `PYTHONPATH=/workspace/.pip`. Every execution emits an audit log entry; dangerous keywords (`rm`, `curl`, `wget`, `sudo`, `sshd`) trigger a warning log but do not block execution. The `bash` tool description also steers the model away from `cat`/`rm`/`ls`/`find`/`sed`/`awk`/`grep` toward the dedicated `xizhi_*` tools via prompt only (no command-input interception — bash is Turing-complete, so substring/regex gating would both false-positive and false-negative). The sandbox also establishes a real writable `$HOME` as an in-namespace tmpfs (forced to the synthetic `/home/blowball` regardless of `allowed_env_patterns`, so a leaked host `HOME` never points into the void), binds the operator tools dir `{data-dir}/tools` read-only onto `$HOME/.local/bin`, and prepends `$HOME/.local/bin` to `PATH` so operator-provided CLIs are invocable by bare name and take precedence over host `/usr/bin`. Known limitation: tools that resolve the home directory via `getpwuid(getuid())` instead of the `HOME` env var still see the host uid's `/etc/passwd` entry (bound read-only from the host); a synthetic `/etc/passwd` override is deferred until a real tool proves to need it.
- `internal/tool/luban/` — skill management tools: `luban_list_skills`, `luban_read_skill`, `luban_install_skill`, `luban_list_skill_files`, and `luban_tree_skill`. `luban_install_skill` `git clone`s a GitHub repo (`--depth 1`) or downloads a single `SKILL.md` (≤500KB) into the requesting user's `data/{userID}/skills/` dir. `luban_read_skill` reads the skill's `SKILL.md` by default, or — with a `path` argument — any text file under the skill directory tree (no longer limited to `.md`; binary files are rejected with a clear error, frontmatter is stripped only when the file starts with `---`). `luban_list_skill_files` and `luban_tree_skill` enumerate a skill's directory (flat list / nested tree), mirroring `xizhi_list_files` / `xizhi_tree`; `name` resolves via `skill.Loader` (user overrides global, same precedence as `luban_read_skill`), optional `path` selects a sub-directory confined the same way as `luban_read_skill`, `depth` (tree only) defaults to 3 and clamps to 10, and hidden entries (e.g. a git-cloned skill's `.git`) are excluded unless `include_hidden` is true. They are the only way to enumerate a skill directory (skills live under `data/{userID}/skills` and `{data-dir}/skills`, outside the xizhi-scoped workspace subtree). These are registered only when an agent's config explicitly lists one of them (`needsLubanTools` in `cmd/blowball/serve.go`).
- `internal/tool/skill/` — the shared `skill.Loader` used by luban (discovers global and per-user skills, reads `SKILL.md` bodies with frontmatter stripped, enforces the per-file size cap); also exposes `Loader.SkillDir` (name→directory resolution) and `ValidateSubPath` (the in-skill-directory path confinement shared by `luban_read_skill` / `luban_list_skill_files` / `luban_tree_skill`).
- `internal/tool/mcpclient/` — external MCP client. Supports `sse`, `stdio`, and Streamable `http` transports. Discovered tools are registered with an optional prefix to avoid collisions.
- `internal/tool/mcp/` — **per-user** MCP tools: `mcp_list_servers`, `mcp_add_server`, `mcp_remove_server`, `mcp_call`, `mcp_list_tools`. Unlike the operator-global MCP path (which connects servers at startup and registers fixed proxy tools in the process-wide registry), per-user MCP is **turn-scoped and workspace-resident**: each user declares their own servers in `{workspaceRoot}/.blowball/mcp/{name}/config.json` (one directory per server), connects lazily within a turn, and authenticates with their own static credentials. The five tools are NOT registered in the base registry; the orchestrator's per-turn `AgentFactory.Build` creates one turn-scoped `*mcp.Manager` (bound to the requesting user's workspace) and registers the family fresh for each turn, so one user's authenticated connection can never be served to another user's turn. The family activates automatically when any agent lists an `mcp_*` tool. **Scope restrictions (enforced):** only the remote HTTP (Streamable HTTP) transport is supported (no per-user `stdio`/`sse`), and only static credentials (`bearer` / `api-key` / `basic`) — OAuth flows are rejected (config `Validate`). **Three leak invariants (test-guarded):** (1) `mcp_list_servers` / `mcp_add_server` / `mcp_remove_server` output redacts credential fields (`"***"`); (2) MCP client logging never echoes auth headers — `mcpclient` has no structured logging and its errors use response bodies/server names, never request headers, so the per-user reuse path cannot leak; (3) `mcp_call` injects auth server-side into the outbound request (the manager's transport factory builds the `Authorization`/header from the config), so the credential never appears in model-visible input or output. `mcp_call(server, tool, args)` validates the tool name and args against the `tools/list` schema cached in the config before the round trip (refreshing once on a cache miss); the whole op is bounded by a configurable total-call timeout (default 10s) with a separate connect timeout (default 5s). **Coexistence with operator MCP:** operator servers (`config.yaml` `mcp.servers`) are unchanged and render under `## MCP Tools`; per-user servers render under a separate `## User MCP Servers` prompt section, and the `mcp_*` meta-tool names never collide with operator proxy tool names. Config: `tools.user_mcp.{connect_timeout, call_timeout}`. The `.blowball/mcp/` namespace is reserved on the agent path (`xizhi.ValidatePath` already rejects `.blowball`), so the agent cannot read a user's keys via file tools — only `mcp_*` manages it.

Agent tool visibility is strictly configured:

- `agents.<name>.tools` lists built-in tools the agent may use.
- `agents.<name>.mcp.servers` grants access to specific MCP servers/tools (`["*"]` for all tools from that server).
- `agents.<name>.skills` lists skill names injected into the system prompt and enables `luban_read_skill`.
- (model-effort-v2) Agents carry NO model/thinking fields — the turn's model, effort, and wire family come exclusively from the catalog + deployment defaults + request params (see per-request model selection above). Residual `agents.<name>.model|thinking|reasoning_effort` keys fail config load.

Skills are `{skill-name}/SKILL.md` files with YAML frontmatter (`name`, `description`). Global skills live in `{data-dir}/skills/` (default `./skills/`); per-user skills live in `data/{userID}/skills/`. User skills override global skills of the same name.

### SSE streaming

`internal/stream/event.go` defines `StreamEvent` and event types: `agent_start`, `token`, `reasoning`, `tool_call`, `tool_result`, `agent_end`, `agent_error`, `done`. `reasoning` carries thinking-mode chunks (emitted when an agent runs with `thinking: true`). `message` is a sentinel type used only for persisted user-message rows; it is never emitted over SSE. Every event produced by a sub-agent Run carries `Meta.parent_tool_call_id` — the parent invoke_* tool_call id that spawned the run (subagent-run-identity capability) — so interleaved parallel same-name invocations stay attributable end-to-end (SSE → `messages.run_id` → frontend segmentation by `(agent, run_id)`); top-level Confucius events never carry the key, and old frontends simply ignore it. The terminal `done` event carries `Meta.usage` in the authoritative nested shape `{total:{prompt_tokens,completion_tokens,total_tokens,reasoning_tokens?}, by_agent:{<agent>:{...}}, meta:{sub_agent_invocations:[...], parallel:bool, round_capped?:true}}` (`round_capped` appears only when an agent hit its cap, after a tool-disabled wrap-up round ran). A cap-hit whose wrap-up yields no content also emits `agent_error` (code `round_cap_exhausted`) and `done.error`. The legacy flat top-level token fields were moved under `total`; frontend consumers reading `usage.total_tokens` must migrate to `usage.total.total_tokens`. On the SSE wire every frame carries an `id:` line (the run event log's Redis Stream entry id, replayable as `Last-Event-ID`) and every event's `Meta.run_id` names the owning turn (turn-detach-resume capability).

- `stream.Hub` (`hub.go`) is a single-consumer buffered channel. Agents produce events via `Send`/`SendCtx`; `Send` is non-blocking and drops on full buffer.
- `stream.WriteSSE` (`sse.go`) consumes the hub and writes `event:` + `data:` SSE frames to the HTTP response, flushing after each event.
- The hub decouples producers from the HTTP writer so slow clients do not block agent loops.

### Persistence

Messages use a **Redis-first write-behind** path (message-write-behind capability) centered in `internal/service/session.go` (`SessionService.SaveMessagesBatch`):

1. Redis (`internal/store/redis/`) — the only synchronous layer. Each turn's batch is minted with per-message `client_msg_id` idempotency keys (UUID) and dual-written in ONE transactional pipeline: `RPUSH msgs:{id}` (read cache, 24h TTL) + `RPUSH msgs:buffer` (global FIFO ingest queue, **no TTL**). If the pipeline fails (Redis down), the batch falls back to a synchronous direct MySQL write (idempotent INSERT + `update_time`), preserving the "messages always win" convention.
2. MySQL (`internal/store/mysql/`) — source of truth; users, sessions, titles, messages. Rows arrive **asynchronously** via the background flusher.

The filesystem warm tier is **removed**: `fs.Store` is shrunk to `EnsureUserDirs` (workspace + `.blowball/skills/` only; `sessions/` is no longer created). Legacy `data/{userID}/sessions/` directories are never read or written; messages that existed only there (pre-change MySQL-write failures) are accepted as lost — operators may clean the directories up.

**Flusher** (`internal/msgflush`, modelled on `internal/llmraw`): constructed and started only by the agent/all roles (the api role never runs the consumption path; it can still call the synchronous drain). Each process runs one flusher goroutine; multiple agent processes share the queue safely. Reliable-queue protocol: atomic `LMOVE msgs:buffer → msgs:processing` claims (≤ `messages.flush_batch_size` per round) → batch `INSERT IGNORE` (the UNIQUE `client_msg_id` index collapses redelivery to one row) → per-record `LREM` ack. Insert failures park the batch in `msgs:processing` and retry after a 1s backoff, never dropping; the single dead-letter exception is a MySQL FK error 1452 (session deleted). Process startup (`Start`) requeues `msgs:processing` residue back onto the buffer head. Each successful batch refreshes `sessions.update_time` once per distinct session (the synchronous per-turn refresh moved here; list freshness lags ≤ `messages.flush_interval`). Triggers: interval ticker (default 1s) + producer nudge once the queue crosses the batch threshold; graceful shutdown runs one bounded final drain. Config: top-level `messages:` block (`flush_interval` default 1s, `flush_batch_size` default 100; explicit negatives rejected at load — see `config.example.yaml`).

**Read path** (`MessageService.RecoverMessages`): Redis first; on a miss (or Redis error) it runs a bounded synchronous drain (`msgflush.Drain`) so queued-but-unflushed messages land in MySQL *before* the read and the `SetMessages` cache backfill cannot erase them; then reads MySQL (`ORDER BY msg_time, msg_index`) and backfills the cache. The history pagination endpoint reads MySQL directly and accepts a read-your-writes window ≤ `flush_interval` (the SSE stream itself is unaffected). **Delete flow** (`SessionService.DeleteSession`): ① bounded synchronous drain (unflushed messages land first so the `*_deleted` archive mirrors are complete; a drain failure aborts the delete) → ② the single-transaction archive+purge → ③ proactive `DEL msgs:{id}` / `session:{id}` (database first, cache second — a behavior change from the previous TTL-only policy).

**Deployment prerequisite**: with the queue as the only synchronous layer, Redis must run with AOF (`appendonly yes`) — a bare-restart Redis loses the flush window's messages. The server probes `appendonly` at startup (best-effort `CONFIG GET`; failure skipped) and WARNs when it is off. See `docs/redis-first-persistence.md` for the deploy/migrate/rollback runbook (including the manual application of migration `012` on existing databases and the wait-for-empty-queue rollback rule).

`internal/store/mysql/message.go` implements cursor-based pagination with a composite cursor `(msg_time, msg_index, id)` clamped to `[1, 200]` items per page.

Each message row carries an `event_type` column and a nullable `run_id` (migration `014_subagent_run_id.sql`, subagent-run-identity capability): the parent invoke_* tool_call id for rows emitted by a sub-agent Run, NULL/empty for top-level and legacy rows. `MergeEvents` treats a run-id change as a merge boundary, so interleaved tokens of concurrent same-name invocations persist as separate per-run attributed rows (arrival order and the deterministic `client_msg_id` idempotency system unchanged); history reconstruction (`MessagesToAgentMessagesIndexed`) and the frontend regroup such rows by `(agent, run_id)`, while tool_call/tool_result pairing stays keyed by `tool_call_id`. Reasoning/thinking output is persisted as ordinary rows with `event_type='reasoning'` (no separate column), so it survives reloads and is replayed into multi-turn context. SQL migrations live in `migrations/`; `docker compose` mounts the whole directory into MySQL's `/docker-entrypoint-initdb.d`, so files run alphabetically on first init. `migrations/011_llm_raw_log.sql` creates the `llm_raw_log` table (llm-raw-capture capability): one row per raw record captured around a single LLM call — `kind` is `request` (as-sent params JSON) / `chunk` (one row per SSE frame, raw = the frame's wire bytes verbatim) / `response` (stitched completion JSON) / `error` (gateway status + raw error body), with every row of one call sharing `call_id`+`seq` and ordered by `frame_index` (replay a turn with `ORDER BY seq, frame_index`). `model`/`finish_reason`/`http_status`/`duration_ms` are materialized redundantly from `raw` for filter-without-parse queries; `raw` is `MEDIUMTEXT`, stored verbatim — no compression ever, no truncation except the 8MB per-call chunk-capture budget. The table deliberately has **no FK to sessions** (rows survive session deletion as orphans — post-mortem for deleted sessions is the use case) and **no cleanup job** (no retention/TTL/background DELETE ever; growth is operator-managed). Existing databases need `011` applied manually — the initdb mount only runs on first volume init. `migrations/010_turn_usage.sql` creates the `turn_usage` table (turn-cost-tracking capability): one row per completed turn carrying `(session_id, trace_id, user_id, usage_json, total_tokens, context_tokens)`, where `usage_json` is the same authoritative usage object emitted on the `done` event (`{total, by_agent, meta}`), `total_tokens` is a redundant copy of `total.total_tokens` for fast per-session `SUM()` cost aggregation, and `context_tokens` (migration 013) records the turn's LAST LLM round prompt+completion — the authoritative end-of-turn context size the turn-start compaction check reads (never the cumulative sum). `migrations/015_turn_usage_model.sql` (per-request-model-selection capability) adds `turn_usage.model VARCHAR(64) NULL` — the model name the turn resolved to (request-selected catalog entry, else the deployment default), stored via `NULLIF` so empty values read identically to pre-migration NULL rows; existing databases must apply `015` manually. `turn_usage` is written by `SessionService.SaveTurnUsage` as an **independent** call after `SaveMessagesBatch` (NOT same-transaction — the store layer has no transaction plumbing and the spec mandates a usage-write failure must not roll back the message batch), and cascades with session deletion via FK `session_id → sessions ON DELETE CASCADE`. The `done` event itself is intentionally excluded from the `messages` log (usage is observability data, not chat content), so `turn_usage` is its durable home. `migrations/008_deletion_archive.sql` creates `*_deleted` mirror tables (`users_deleted`, `sessions_deleted`, `titles_deleted`, `messages_deleted`) that archive rows verbatim before a session is purged — `SessionService.DeleteSession` drains the write-behind queue first (so unflushed messages are archived too), then copies the session/titles/messages into the mirrors in a single transaction, deletes the live `sessions` row (cascade clears titles/messages), and finally clears the Redis `msgs:{id}` / `session:{id}` keys. The mirrors carry no foreign keys and `messages_deleted.id` is a plain `BIGINT` preserving the source id; `users_deleted` is scaffolding, not yet written. `migrations/012_client_msg_id.sql` adds the `client_msg_id` column + UNIQUE index `uk_messages_client_msg_id` backing the write-behind idempotency (legacy rows keep NULL; existing databases must apply `012` manually). `migrations/013_context_compaction.sql` (context-compaction capability) widens `client_msg_id` to `CHAR(64)` — the mid-turn flush's deterministic ids are `{trace_id}:{msg_index}` and a UUID trace_id alone already fills 36 chars — and adds the compaction-side schema (see the context-compaction section above; existing databases must apply `013` manually). `migrations/014_subagent_run_id.sql` (subagent-run-identity capability) adds `messages.run_id CHAR(64) NULL` (existing databases must apply `014` manually; deliberately no index — every read path fetches by session and groups in memory). Turn persistence stamps deterministic ids for every row (`{trace_id}:{msg_index}`; user row `:0`, merged events `:1..N`) so the mid-turn flush and the turn-end save are idempotent against each other; rows written before 013 keep UUID/NULL ids.

### Frontend

The React 19 + Vite + TypeScript frontend lives in the separate `blowball-frontend` repo. The API contract is defined here in `api/openapi.yaml`; when it changes, copy that file into `blowball-frontend/` and run `npm run generate-api` there to regenerate `src/lib/openapi.d.ts`.

## Important conventions

- **Config**: `internal/config/config.go` loads YAML and expands `${VAR}` / `${VAR:default}` from the environment. Durations support short suffixes (`s`, `m`, `h`, `d`, `w`).
- **LLM stream idle timeout**: `openai.stream_idle_timeout` (opt-in inter-frame idle cap on streaming LLM calls, recommended `2m`; zero/unset = disabled, negative fails config load) — a stalled stream aborts with a typed error that the transient classifier routes into the existing retry pipeline. See Agent orchestration / stream idle watchdog above.
- **Length continuation**: `openai.length_continue` (`{expand_step: 8192, max_retries: 3}`; zero/unset block = disabled, any non-zero field enables with defaulted siblings, negatives fail config load) — a `finish_reason=length` round is continued (partial output kept, budget expanded per attempt, ≤ `max_retries` continuations) instead of silently ending the turn; exhaustion emits `agent_error(length_exhausted)` + `done.error`. See Agent orchestration / length continuation above.
- **Model catalog**: `openai.models` (mandatory list of `{name, max_context_tokens, thinking}`) + `openai.default_model` (default entry) + `openai.default_reasoning_effort` (deployment effort default, unset → none) + `openai.title_model` (title-only model, unset → default entry) drive per-request model/effort selection on `POST /messages` and the `GET /api/v1/models` endpoint (model-effort-v2). An empty catalog fails config load. Catalog entries require unique non-empty names and positive-integer windows (shadow-checked against yaml fraction truncation); `default_model` must name an entry; `default_reasoning_effort` is a closed set. The removed legacy keys (`openai.model`, top-level `openai.max_context_tokens`, `agents.<name>.model|thinking|reasoning_effort`) are rejected at load with migration-pointing errors. See Agent orchestration / per-request model selection above.
- **Tool execution timeouts**: `tools.timeouts` (`ToolsConfig.Timeouts`, `map[string]time.Duration`) maps a built-in tool name (the same identifier agents list under `tools:`) to a per-invocation execution budget. It is enforced centrally at the registry dispatch entry point: `Registry.Call` (`internal/tool/registry.go`) derives a `context.WithTimeout` child for any tool mapped to a positive duration before invoking `Execute`, so it bounds every tool that flows through the registry across all three agents and MCP proxies. An absent entry or a zero/negative duration is unbounded (byte-for-byte prior behavior) — the feature is opt-in per tool with no global default. For remote tools that already have a native timeout (`webfetch` / `bash` / per-user `mcp`), the central timeout is a looser outer backstop (set it looser than the native one so the tighter bound fires first); for the timeout-less local tools (`xizhi_*`, `luban` list/read) it is the first and only bound. The map is applied via `Registry.SetTimeouts` at both the process-wide registry (`cmd/blowball/serve.go`) and the orchestrator's per-request execution registry (`internal/agent/orchestrator.go`). See `config.example.yaml` for the commented example block.
- **Sandbox directory configuration**: the process-level Landlock baseline and the per-command bwrap executor sandbox are operator-configurable with zero-behavior-change defaults. Top-level `landlock` (`LandlockConfig`) controls the process sandbox: `enabled` (default `true`, `*bool` nil→enabled like `PipToolConfig.Network`; `false` skips `ApplyLandlock` warning-only), `system_read_only` (stat-guarded read-only baseline, default `[/etc /usr /bin /lib /lib64 /proc]`), and `extra_read_write`/`extra_read_only` (extra absolute process RW/RO dirs). `tools.executor.sandbox` (`ExecutorSandboxConfig`) controls the bwrap sandbox: `system_read_only` (stat-guarded baseline, default `[/usr /bin /lib /lib64 /etc]`), and `extra_read_only`/`extra_read_write` (operator datasets/caches; each entry is `host` or `host:target`, parsed at load into `MountSpec`). Both baselines are stat-guarded — a missing entry (e.g. `/lib64` on aarch64) is skipped rather than failing startup, fixing the pre-configurability bwrap `/lib64` boot failure. The process RW/RO application dirs (`{d}/data`,`{d}/logs`,`{d}/skills` / `{d}/tools`) are still derived from `-d` and are NOT configurable here. The load-bearing bwrap invariants (`/workspace`, synthetic `$HOME`, `$HOME/.local/bin`, skills targets, `--chdir`, `PYTHONPATH`) are fixed and not configurable. `validate()` guards: every configured dir/mount host must be absolute; `extra_read_write` rejects `"/"`; extra-mount `target` must not collide with `/workspace`,`/home`,`/skills`,`/tmp`,`/proc`,`/dev` or a system-baseline entry; and `ValidateLandlockRW` (called from `setupRuntime`) requires ≥1 effective RW dir when landlock is enabled. `tools.executor.bash.env` (operator `KEY: value` env-literal map) is the operator-configurable env surface and is also validated at load: `HOME` is reserved and key names must match `^[A-Za-z_][A-Za-z0-9_]*$`. It forms the middle tier of the three-tier sandbox env (host allowlist < `env` literals < forced invariants — see **Executor tools (Linux only)**); the forced `HOME`/`PATH`/`PYTHONPATH` invariants are not operator-configurable. `extra_*` dirs never participate in the shared-storage `{data-dir}/data` health-check/FUSE anchor.
- **Workspace storage backend**: `storage.workspace.backend` (`internal/config/config.go`, `StorageConfig`) selects where the per-user data root `{data-dir}/data` physically lives: `local` (default, each process's local disk) or `shared` (operator-mounted shared POSIX filesystem — MinIO-backed JuiceFS). Default is zero-behavior-change. In `shared` mode `setupRuntime` runs a startup health check (`internal/storage`, before Landlock) that verifies `{data-dir}/data` is writable and FUSE-family, refusing to boot otherwise so a node can never silently degrade to local disk and diverge from the cluster; when executor tools are configured on an agent/all role, `internal/tool/executor.ProbeFUSEWorkspace` additionally self-checks that the mount allows a user-namespace-mapped uid (i.e. JuiceFS `--allow-other`). All POSIX file ops (`xizhi_*`, `WorkspaceHandler`, `fs.Store`, executor `--bind`, `onlyOfficePersist` rename) are unchanged in shared mode — only the mount point changes. See `docs/shared-storage.md` for the deploy/migrate/backup runbook.
- **Context values**: `TraceMiddleware` mints `trace_id`; `AuthMiddleware` injects `userID`. Both propagate through stores via context. The skill tool reads `userID` from context to scope skill lookups.
- **Not-found handling**: MySQL and filesystem store methods return `(nil, nil)` on missing records, not errors.
- **Security**: there is no public user-creation endpoint; users are created via the `blowball seed` subcommand. Workspace file tools enforce per-user path scoping at the application layer; Landlock is a best-effort extra layer on Linux. Landlock is scoped to the four runtime subdirs — read-write for `{d}/data`, `{d}/logs`, `{d}/skills` (the logs dir is covered for lumberjack's post-rotation reopen) and read-only for the operator tools dir `{d}/tools` (mirroring the in-sandbox `--ro-bind`); in production point `-d` at a dedicated directory rather than the repo root to keep the sandbox tight. The Landlock and bwrap system read-only baselines and any extra dirs/mounts are operator-configurable (see **Sandbox directory configuration** above) with defaults that reproduce the pre-configurability behavior, bounded by `validate()` guards against over-broad/non-absolute/colliding paths. In `storage.workspace.backend: shared` mode the per-user data subtree lives on a shared FUSE mount (JuiceFS) that must be mounted with `--allow-other` (and `/etc/fuse.conf` `user_allow_other`) so the bwrap sandbox's mapped uid can access `/workspace`; `validatePath` symlink defense, path scoping, and the bwrap namespace all remain in force, and access is still gated by JWT auth, so the wider FUSE uid access is bounded to authenticated, path-validated operations on a controlled server host.
- **Login policy**: `auth.password_required` (in `internal/config/config.go`, `AuthConfig`) toggles whether `POST /api/v1/auth/login` verifies the password. It defaults to `true` (bcrypt verified against the seed-created hash). Set `auth.password_required: false` for passwordless login — `AuthService.Login` skips bcrypt, so any seeded, active user logs in by username alone (a sent password is ignored). The flag is threaded into `service.NewAuthService` from `cfg.Auth.IsPasswordRequired()` in `wireAPI`; the handler and frontend are mode-agnostic.
- **Prompt rendering**: `internal/prompt/render.go` assembles the system prompt with environment info, built-in tools, MCP tools grouped by server, and skills as XML tags.
- **Message reconstruction**: `internal/handler/message_reconstruct.go` rebuilds agent-ready conversation history from persistence, tracking tool-call state across messages.
- **Testing**: unit tests are per-package; integration tests in `test/integration/` exercise real handlers/services/orchestrator with faked MySQL, Redis, and LLM.
